# comiketDiscord 設計書

## 1. 目的とスコープ

コミケ当日の購入対象と進捗を Google Sheets で管理し、Discord 上で複数の購入担当者がリアルタイムに共有できる Bot を作る。初期版では運用を単純に保ち、独立したデータベースは導入しない。

## 2. 合意済みの基本設計

### データの責務

- Google Sheets を購入対象・必要数・例外状態・引継ぎ情報などのマスタ兼永続ストレージとする。
- Discord のリアクションを通常購入（1人1個）の入力・状態として扱う。
- 独立した DB は初期版では導入しない。Sheets／Discord だけで不足する要件や同時更新上の問題が明確になった時点で再検討する。
- Embed の表示内容を更新処理の正とはせず、Sheets と Discord のリアクションから再計算する。

### Discord 表示

- 購入対象を場所順に並べ、場所をまたがない固定の最大10件単位で Embed メッセージを作る。
- 各メッセージの1〜10番と `1️⃣`〜`🔟` を対応させる。
- ページ送りボタンは使わない。11件目以降は後続の別メッセージとして最初から表示する。
- `Discord message ID + reaction number` から対象 item を一意に解決できるようにする。

### 通常購入

- ユーザーが番号リアクションを追加すると、そのユーザーによる通常購入1個分として数える。
- 同じ番号に複数ユーザーがリアクションしてよい。各ユーザーの寄与を合算する。
- リアクションを外すと、そのユーザーの通常購入1個分を取り消す。
- Bot 自身のリアクションは購入数に含めない。
- 番号リアクションは対応するサークル（Field）内の全商品に対する購入として扱う。
- 表示状態は `0 = 未購入`、`1以上 = 完了` とする。

### 例外処理

- 引継ぎ、売切れ、1人が同一対象を2個以上購入した場合など、リアクションだけで表せない状態は Discord Components と Modal で入力する。
- 現在の試作では例外情報をメモリに保持し、対象商品の `備考` として Embed の再描画時に反映する。Bot再起動後の復元は対象外とする。
- Modal の具体的な項目、更新権限、数量の集計規則は未決定とする。

## 3. 想定構成

```text
Google Sheets（マスタ／例外情報）
        │ 読み書き
        ▼
TypeScript Discord Bot（コンテナ）
        │ 投稿・再取得・更新
        ▼
固定 Embed メッセージ群 + 番号リアクション + Components／Modal
```

初期データモデルの候補：

- `Items`: `itemId`, `location`, `circle`, `product`, `requiredQuantity`, `price`, `order`, `status`, `handoverMemo`
- `MessageMappings`: `guildId`, `channelId`, `messageId`, `slot`, `itemId`, `lastRenderedAt`
- `PurchaseOverrides`: `itemId`, `discordUserId`, `quantity`, `state`, `memo`, `updatedAt`, `updatedBy`

購入候補の入力は `PurchaseCandidateSource` を境界とし、現在はCSVアダプターを使用する。Google Sheetsアダプターは、スプレッドシートIDと `イベント識別子-日数-会場`（例: `C107-2-東`）形式のシート名でタブを取得し、同じ行変換処理へ渡す。各行の `itemId` は日程・配置から生成せず、CSV／シートに保存したランダムな16桁16進数を安定IDとして扱う。

シート名と列は実装前に確定する。安定した `itemId` を行番号とは別に持つ。

## 4. イベント処理案

1. Reaction Add／Remove を受信する。
2. `messageId + emoji` から `itemId` を解決する。
3. 対象メッセージのリアクションユーザーを Discord から再取得する。
4. 通常購入数と Sheets の例外数量・状態を規則に従って再計算する。
5. 対象メッセージ単位で Embed を再生成し、内容に差分がある場合のみ更新する。

イベント payload や現在の Embed 表示だけを信用せず、再取得可能な状態から冪等に再計算する。競合時の上書きを避けるため、更新は少なくともメッセージ単位で直列化・短時間にまとめる。

## 5. 再起動・復旧

- `messageId` と各 slot の `itemId` の対応を Sheets に保存する案を第一候補とする。
- 起動時にマッピングと Discord メッセージを検証し、欠損・削除・権限不足を報告する。
- 管理コマンドで全再同期／特定メッセージ再同期を行えるようにする。
- 投稿途中で失敗しても再実行で重複投稿しない識別方法を決める必要がある。

## 6. 残っている決定事項

優先度が高い順に、実装前または初期実装中に決める。

1. **Discord ライブラリ**: 第一候補は `discord.js`。代替案を含め、必要な Components／Modal と保守性で決定する。
2. **Sheets 認証**: Google Cloud サービスアカウント、Workload Identity 等の方式、鍵の保管場所、対象シートの共有方法を決める。
3. **複数個購入の永続化と集計**: Override がリアクションの1個を「置換」するか「追加」するか、重複計上をどう防ぐかを確定する。
4. **メッセージマッピングと復旧**: Sheets 保存形式、初回投稿、再投稿、削除済みメッセージ、シート行の並べ替えへの対応を決める。
5. **同時更新**: メッセージ単位のキュー、debounce、Sheets 更新時の競合検知、API rate limit／retry 方針を決める。
6. **コマンド**: `/publish`, `/sync`, `/status`, `/handover` 等の要否、利用可能な guild／channel、管理者限定操作を決める。
7. **権限と Intents**: Guilds、Guild Message Reactions、メッセージ／リアクション取得に必要な権限、Bot ロールと Modal 操作権限を最小化する。
8. **デプロイ／コンテナ**: 実行先、Node バージョン、常時稼働、secret 注入、タイムゾーン、ヘルスチェック、再起動ポリシーを決める。
9. **ログ・監視**: 構造化ログ、個人情報の扱い、監査ログ、通知先、保持期間を決める。
10. **エラー処理**: Discord／Sheets 障害時の retry、部分失敗、利用者への ephemeral 応答、復旧手順を決める。
11. **テスト**: 集計・分割・マッピングの単体テスト、API adapter の結合テスト、検証用 guild／Sheet を使う E2E テストを決める。

## 7. 初期実装の境界

- TypeScript、Node.js、コンテナ実行を前提とする。
- Discord／Sheets は adapter として分離し、集計・10件分割・表示生成を外部 API なしでテスト可能にする。
- 初期スケルトンでは接続ライブラリや認証方式をまだ固定しない。
- secret は環境変数等で注入し、Git やコンテナイメージへ含めない。

## 8. 初期受け入れ条件

- 場所順の対象が、場所をまたがず最大10件の固定メッセージ群に分割される。
- 同じ番号への複数ユーザーのリアクションを個別に数え、Remove で該当ユーザー分だけ戻せる。
- 復旧後も同じ `messageId + slot` が同じ `itemId` を指す。
- 例外数量・売切れ・引継ぎを保存し、通常リアクションと定義済み規則で統合表示できる。
- 同一イベントの再処理で購入数が二重加算されない。
